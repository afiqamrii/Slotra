# UI and booking review — 16 November 2026

This review improves the existing reception and guest booking journeys. It preserves the current visual language, tenant authorization, server-calculated prices and payment boundaries. The working tree already contained substantial implementation changes; this document records this review's changes, not ownership or acceptance of every existing feature.

## Prioritized follow-up

1. **Production acceptance:** run booking/payment/resource-move races through two independent PostgreSQL connections on an isolated staging database. PGlite confirms domain behavior and constraints in one backend; it cannot establish the production locking behavior. See `BOOKING_ENGINE.md` and `RELEASE_CHECKLIST.md`.
2. **Payments and subscriptions:** complete venue-owned live gateway onboarding, signed-event verification, late-payment reconciliation and provider-supported refunds; accept recurring SaaS collection separately. Existing TestProvider/ToyyibPay and subscription simulators are development capabilities. See `PAYMENTS.md`, `SAAS_BILLING.md` and `INTEGRATION_READINESS.md`.
3. **Refund interpretation:** keep cancellation separate from refunds. The ledger currently computes outstanding as total minus net paid, so refunding an active booking can increase its displayed outstanding amount. Any alternative such as waived charges or cancellation fees needs an explicit financial policy and ledger design, not a UI-only adjustment. Manual refunds record money returned outside the app.
4. **Broader accessibility acceptance:** complete keyboard, screen-reader, contrast and 375/390/430px/tablet/desktop checks beyond these booking screens, especially Grow/Pro forms and reporting charts. Existing `DESIGN_SYSTEM.md` explicitly leaves broad visual/keyboard acceptance open; this review does not claim defects or acceptance for untested screens.
5. **Remaining failure-path browser coverage:** exercise customer-search transport failure, membership/credit changes, unavailable guest grids, stale quotes, conflicting submissions and waitlist focus on the isolated fixture. Successful staff/guest saves and navigation were verified in this review. Add integration coverage where browser testing identifies remaining gaps; helper tests alone do not exercise asynchronous UI transitions.

No deployment, production migration, live payment activation or external delivery acceptance is implied by this review. Current release gates remain in `RELEASE_CHECKLIST.md`.

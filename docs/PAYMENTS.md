# Booking payments

**Phase 7 foundation:** Manual/Cash/Bank Transfer, a local TestProvider, and a ToyyibPay hosted-bill **sandbox** adapter are implemented. The sandbox moves no real funds and is disabled in production. No live online merchant gateway is connected. Slotra does not receive or custody venue booking funds; production public checkout remains Pay at venue.

Professional and higher plans include `ONLINE_PAYMENTS`, `DEPOSITS`, and `ONLINE_REFUNDS` entitlements, while Starter remains manual/pay-at-venue only. Professional Settings → Payments identifies online payments as available *with the plan* but distinguishes that from a connected **live** provider. TestProvider and ToyyibPay sandbox remain explicitly nonproduction. No per-venue production merchant connection, live FPX/card/DuitNow checkout, or real SaaS subscription charge is implemented. The separate one-time Professional upgrade test uses the same ToyyibPay sandbox category but **not** the venue-booking payment ledger.

Business inherits the Professional payment entitlements; Step 14 does **not** create a new gateway or change who holds venue funds. Business price rules determine the server subtotal before membership discounts, promo discounts, or a whole-booking package/membership-credit redemption. `paymentDue` then calculates any online amount from the resulting server total, and the booking snapshots subtotal, discount, total, due now, paid, and outstanding. A fully credit-covered or 100%-discounted booking has zero due now and can confirm without pretending an online payment succeeded. A promo code sent by the browser is only a requested code; the service validates its terms and computes the actual discount. Staff-administered membership assignment and package issuance do not create a payment record or charge the plan's listed price. Selling these plans online, recurring membership billing, automated credit renewal, and provider-managed refunds require separate payment-domain work.

## One-time Professional sandbox upgrade test

An authenticated Starter owner can enter a contact number at Settings → Plans and request an RM129 ToyyibPay **sandbox** bill. The server snapshots the price in minor MYR units in `plan_upgrade_attempts` and creates a separate bill with the attempt UUID as its external reference. The bill returns to a workspace status page and posts to a separate sandbox callback route. The callback checks ToyyibPay's documented MD5 hash in constant time, but **does not rely on it alone**: the server calls `getBillTransactions` and matches bill code, external UUID, exact amount, and successful transaction status. The return page performs the same server-side inquiry because ToyyibPay cannot call localhost. Only then does an organization-row-locked transaction change Starter to Professional. Replay returns the existing PAID state; failed or mismatched payment keeps Starter. An active attempt is reused rather than opening multiple bills.

The sandbox is disabled in production, uses the existing shared test category only for development, and moves no real money. This is a one-time persistent test entitlement, **not** a recurring RM129 subscription: there is no period renewal, cancellation, proration, invoice, downgrade, or automatic expiry. A real Slotra billing integration must use Slotra's own production merchant account and a separate subscription design; venue booking funds must still flow directly to each venue's merchant account. [ToyyibPay's API reference](https://toyyibpay.com/apireference/) documents bill creation, callback verification, and transaction inquiry.

## Money flow and boundary

Customer → venue merchant account at a provider → signed provider event/server verification → Slotra payment ledger and booking state. The private `app` schema is server-only; no raw card details, API private keys, access tokens, or webhook secrets live in general application tables or browser bundles. A future provider should use provider-managed OAuth or encrypted server-side credentials with rotation. `organization_payment_accounts` holds only a provider name, merchant account identifier, connection/default status, and timestamps. Do not treat a row inserted manually as an operational connection; the adapter registry must support it.

`src/lib/payment-providers.ts` defines the adapter contract for creation, status lookup, refunds, and webhook verification. `ManualProvider` records an authorized staff assertion after cash/bank transfer/other manual money has actually been received; it does not perform a charge. A manual refund is a staff record made only after funds have actually been returned outside Slotra. Staff may record partial manual receipts and multiple receipts against one booking, capped by its outstanding balance; manual refunds remain available on Starter. `TestProvider` signs/verifies HMAC-SHA256 events and simulates outcomes; it moves no money, only runs when `NODE_ENV !== production`, `ENABLE_TEST_PAYMENTS=true`, and `TEST_PAYMENT_WEBHOOK_SECRET` is present. It cannot be connected or invoked in production. No fake live Stripe/CHIP/ToyyibPay account or production success response is present. The real ToyyibPay sandbox API is integrated separately below.

To add a real provider, implement the adapter with venue merchant-account onboarding, credentials in a managed secret store, an authenticated provider callback, provider-specific event mapping to normalized states, idempotency keys for checkout/refund creation, and an independent provider status reconciliation task. Register it only after security, tenant ownership, merchant-funds routing, and production acceptance review. Do not make network calls while holding a resource or booking row lock; initiate provider sessions outside the short reservation transaction and handle failures/expiry explicitly.

## ToyyibPay hosted-bill sandbox

The sandbox adapter uses only `https://dev.toyyibpay.com` and never sends the secret key to a browser or stores it in the database. Configure `ENABLE_TOYYIBPAY_SANDBOX=true`, `TOYYIBPAY_SANDBOX_SECRET_KEY`, and `TOYYIBPAY_SANDBOX_CATEGORY_CODE` in a git-ignored server environment. Set `TOYYIBPAY_SANDBOX_ORGANIZATION_ID` to bind one venue, or explicitly set `TOYYIBPAY_SANDBOX_SCOPE=ALL_TEST_VENUES` to share one **test-only** merchant account across development venues. Even with shared credentials, each venue has its own account row, booking, payment, and authorization boundary. Each owner/admin connects the sandbox under Settings → Payments, where the category is checked against ToyyibPay before marking it connected. A live deployment must **not** share Slotra's merchant account across venues; each venue needs its own merchant onboarding and secret management.

A guest booking still snapshots the server price and due-now amount in a short resource-locked transaction. After commit, the adapter creates a fixed-amount MYR bill in cents with `billExternalReferenceNo` equal to the internal payment UUID and a `billExpiryDate` matching the booking hold. No network request runs while the resource is locked. The customer is redirected to ToyyibPay's hosted sandbox bill. The booking confirmation token is held in a short-lived HttpOnly, SameSite=Lax return cookie, not sent to ToyyibPay in the return URL. An uncertain bill-creation failure expires the hold; staff must review any late verified money separately.

ToyyibPay's documented callback supplies `hash = MD5(userSecretKey + status + order_id + refno + "ok")`. The callback handler validates this in constant time and matches the bill code/payment, then independently calls `getBillTransactions`. It requires the stored bill code, matching external payment UUID, exact amount, and successful transaction state before the existing idempotent payment state machine may confirm the booking. A repeated callback is harmless. Browser `status_id` is ignored. On browser return, the server performs the same independent transaction check before displaying confirmation. The private confirmation page also offers a rate-limited manual status check if a callback or return is missed. ToyyibPay cannot send callbacks to localhost; local sandbox testing relies on these server-side status checks or a public test tunnel/deployment. A pending or mismatched transaction never confirms the booking. A verified payment after hold expiry is recorded for review, never used to reclaim the slot.

ToyyibPay does not document a refund API in the integration used here. The sandbox refund control is hidden and server-side refund requests are rejected; no refund is claimed. Production mode disables this sandbox adapter and endpoint regardless of environment variables. Before a live gateway launch, use each venue's own merchant credentials, establish secure secret storage and rotation, configure a public HTTPS callback and a hold-expiry scheduler, test independent PostgreSQL concurrency, and arrange operational reconciliation. See [ToyyibPay's API reference](https://toyyibpay.com/apireference/) for the sandbox URL, bill, callback, and transaction fields.
## Plan entitlements and safe rollout

`organizations.plan_code` defaults to `STARTER` and is constrained to Starter, Professional, Business, or Pro. `ONLINE_PAYMENTS`, `DEPOSITS`, and `ONLINE_REFUNDS` inherit through the centralized entitlement map. Starter can create Pay-at-venue bookings, record partial cash/bank-transfer receipts, track outstanding balances, and record manual refunds; it cannot connect an online adapter, save an online/deposit policy, create an online hold, or request a provider refund through owner actions. The server checks this even for direct action calls. Professional and higher may use online functionality only where a genuine supported adapter is configured; the existing TestProvider and ToyyibPay sandbox remain development-only. Existing venues migrated to Starter retain account and historical ledger rows but new online checkout is masked. Verified events for pre-existing holds still reconcile, even after downgrade; do not discard money because of a plan change. Old online policy settings must be reviewed before a future upgrade re-enables them. Apart from the nonproduction one-time Starter → Professional sandbox test, plan assignment remains operator-controlled and there is no live SaaS purchase or recurring charge.

## Policy and booking snapshot

Money is stored in integer minor currency units (for MYR, RM30.00 = 3000 sen). Percent deposits round once on the server; clients cannot set the saved total or due-now amount. Settings → Payments stores a per-organization rule: No upfront payment, Full, Fixed deposit, or Percentage deposit. Fixed amount and percentage are validated; the deposit is capped at the booking total and percentage is rounded once to the nearest minor unit. `paymentDue` runs server-side on the existing booking engine's immutable base quote; a guest-submitted price is only a stale-price comparison. On creation, the booking stores `payment_requirement`, `required_now_minor`, and nullable `hold_expires_at`, preserving historical terms when settings change. `payments` holds one normalized charge attempt, and `refunds` records partial/full returns. Booking `amount_paid` is recomputed as PAID/PARTIALLY_REFUNDED/REFUNDED payment amounts minus SUCCEEDED refunds under a booking lock. It is never blindly incremented by a webhook amount. Outstanding is `total_amount - amount_paid`.

When the owner enables manual payment, guests may choose Pay at venue alongside an enabled sandbox checkout. Pay at venue creates a CONFIRMED guest booking with no payment row; any nonzero balance remains outstanding and staff can record a genuine manual receipt later. Guest selection is validated against current organization settings in the server transaction. The chosen manual mode is represented by the immutable NO_UPFRONT booking snapshot; this phase does not expose separate bank-transfer instructions or pretend a transfer was received. An online requirement creates AWAITING_PAYMENT and a pending payment within the same booking transaction. Only a verified paid event before hold expiry makes it CONFIRMED. A browser return or public confirmation view never confirms it. Failure or expiration makes it EXPIRED, releasing the slot. If a signed payment arrives after expiry or cancellation, the payment is recorded as paid and audited as `LATE_PAYMENT_REQUIRES_REFUND`, but the booking is not confirmed or reinserted into an occupied slot. Staff must review and arrange a refund separately. Cancellation does not refund automatically.

Holds default to 10 minutes, configurable from 5–30 in payment settings. They are protected by the PostgreSQL partial GiST exclusion constraint alongside active reservations; old AWAITING_PAYMENT rows with null expiry remain legacy non-holds. Availability excludes expired holds immediately, and creation expires stale holds while holding the resource lock. `POST /api/internal/expire-payment-holds` provides a secret-protected batch sweep. Set `PAYMENT_HOLD_SWEEP_SECRET` and schedule it at least every minute in a real deployment; no production scheduler is configured in this repository yet. The direct SQL constraint cannot use a volatile `now()` predicate, so raw SQL writes against a stale hold require the sweep first. The service path releases it opportunistically. Production online payment must not be enabled until the worker, real adapter, and independent-connection race acceptance are deployed.

## Webhooks, idempotency, and refunds

`POST /api/payment-webhooks/test` reads the raw body and requires the signed `x-slotra-test-signature` header. It exists only in explicitly enabled development. The signature is compared in constant time; invalid input is rejected before database mutation. `payment_webhook_events` has a globally unique provider/event identifier. Event claim, payment update, booking transition, ledger recomputation, and audit are one transaction; duplicate delivery returns a harmless duplicate result. Payment-provider IDs are unique; test IDs use the payment UUID. Staff receipt and refund submissions carry a stable UUID retry key, unique within the organization; a repeat returns the original row without recording a second financial event. Reusing a key with different details is rejected. A real adapter must use a provider-supplied stable event ID, not a fresh UUID on retry. The developer simulator deliberately generates signed events on the server and is never shown as a real checkout.

Refund requests lock the resource, booking, and payment in that order. Pending/processing/succeeded refund amounts count against the refundable balance to prevent concurrent over-refunds. A refund is first persisted PENDING, the provider call runs outside the lock with the refund UUID as the future idempotency key, and completion/failure is recorded separately. Manual and test adapters complete synchronously; future async gateways should leave PROCESSING until verified. Refunds do not change booking lifecycle. Audit records cover manual receipt, settings, provider connection/disconnection, refund request/completion/failure, and late paid events. No sensitive payload is logged.

## Permission, tenancy, and rollout

`payment:view` is granted to all existing roles with booking view; `payment:record_manual` to owner/admin/manager/staff; `payment:refund` to owner/admin/manager; and `payment:manage_settings` to owner/admin only. Every staff action rechecks active membership, then scopes bookings, payments, refunds, and accounts by the selected organization. Composite foreign keys maintain organization ownership and require each refund booking to match its payment booking. Public lookup resolves slug server-side and requires the unguessable confirmation token; no reference-only payment lookup exists.

The test simulator requires `ENABLE_TEST_PAYMENTS=true` and a unique `TEST_PAYMENT_WEBHOOK_SECRET` on a disposable development database only. Never enable or seed it on the connected main Supabase project. For local acceptance, use a dedicated dev `DATABASE_URL`, migrate and seed it, sign in as the venue owner, connect TestProvider, then select Full/Fixed/Percentage and submit guest bookings. Test success, failure, pending, expiry, signed replay, manual payment, and refunds there. Production pay-at-venue remains usable without these flags. Real online payment, external provider reconciliation, a configured production hold scheduler, independent PostgreSQL race acceptance, and real financial operations review are remaining launch gates. SaaS plan billing is entirely separate. The planned Starter plan is manual/offline only; Professional and higher inherit online payments and deposits. Payment feature entitlements are enforced from the trusted plan code; SaaS subscription state and billing are not implemented. Production checkout still requires a live provider and launch gates.

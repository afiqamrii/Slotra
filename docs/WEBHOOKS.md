# Pro outbound webhooks — queue foundation

Pro owners/admins can register a named public HTTPS endpoint, choose event types, disable it, queue a test event, and inspect up to 50 recent delivery records. Initial names are `booking.created`, `booking.confirmed`, `booking.rescheduled`, `booking.cancelled`, `booking.completed`, `payment.paid`, `payment.refunded`, and `customer.created`. Events are created from booking/payment transactions with minimal IDs/status/amounts; no secrets or full customer/payment payloads are included. `(organization_id, idempotency_key)` prevents duplicate event creation, and `(event_id, endpoint_id)` prevents duplicate deliveries.

Secrets are derived server-side by HMAC from a dedicated `SLOTRA_WEBHOOK_SIGNING_KEY` and endpoint ID/version; the derived signing secret is shown once at creation. `signWebhookPayload(secret, body, unixSeconds)` produces header `X-Slotra-Signature: t=<timestamp>,v1=<hex HMAC-SHA256(timestamp + "." + rawBody)>`. Consumers must compare in constant time, enforce a short timestamp tolerance, and reject replayed event IDs. Secret rotation increments the version and invalidates the old derived secret. The master key must live in managed environment secrets and remain stable through deployment rotation.

The schema records pending/succeeded/failed status, attempts, response status, safe error summary, and next retry. Retry delays are designed as 1, 5, 30, 120, and 360 minutes, then stop. **No external delivery worker is connected.** The app does not send queued or test events over the network. The outbound egress implementation was blocked pending explicit approval of sensitive payloads and owner-configured destinations; do not claim a webhook was delivered from a queued row. Before enabling delivery, add approved egress controls against SSRF/DNS rebinding, a protected worker/scheduler, timeout/redirect policy, claim/recovery logic, observability, and independent-connection retry tests.

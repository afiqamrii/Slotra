# Pro outbound webhooks — queue foundation

Pro owners/admins can register a named public HTTPS endpoint, choose event types, disable it, queue a test event, and inspect up to 50 recent delivery records. Test events are limited to ten per actor/organization per hour. Configuration rejects literal IPv4/IPv6, localhost (including a trailing dot), local/internal or single-label hostnames, credentials, fragments and nonstandard ports. This is configuration validation only: a future sending worker must independently resolve/pin public IPs at connection time to defend against DNS rebinding. Initial names are `booking.created`, `booking.confirmed`, `booking.rescheduled`, `booking.cancelled`, `booking.completed`, `payment.paid`, `payment.refunded`, and `customer.created`. Events are created from booking/payment transactions with minimal IDs/status/amounts; no secrets or full customer/payment payloads are included. `(organization_id, idempotency_key)` prevents duplicate event creation, and `(event_id, endpoint_id)` prevents duplicate deliveries.

Secrets are derived server-side by HMAC from a dedicated `SLOTRA_WEBHOOK_SIGNING_KEY` and endpoint ID/version; the derived signing secret is shown once at creation. `signWebhookPayload(secret, body, unixSeconds)` produces header `X-Slotra-Signature: t=<timestamp>,v1=<hex HMAC-SHA256(timestamp + "." + rawBody)>`. Consumers must compare in constant time, enforce a short timestamp tolerance, and reject replayed event IDs. Secret rotation increments the version and invalidates the old derived secret. The master key must live in managed environment secrets and remain stable through deployment rotation.

The schema records pending/processing/succeeded/failed status, claim attempts, response status, safe error summary, and next retry. **The application remains queued-only: no HTTP transport, delivery route, scheduler registration, or enablement flag is connected.** Queuing an event or test ping does not send it or establish delivery. The local worker foundation accepts an explicitly injected transport; automated tests supply fake transports and do not contact an endpoint.

`claimWebhookDeliveries` claims up to ten due records in a short transaction using `FOR UPDATE SKIP LOCKED`. Claims increment `attempt_count` and use the organization, delivery, attempt count and `last_attempt_at` as a receipt fence, with a ten-minute lease. An abandoned lease may be recovered; an expired claim or an old/duplicate receipt cannot overwrite its replacement. A disabled endpoint, unsubscribed event, inactive organization or unavailable Pro entitlement is marked failed without dispatch. Endpoint activation and effective entitlement are checked again before preparing each request. No database lock is held while an injected transport runs.

The stable JSON envelope is `{ "id": "event UUID", "type": "event type", "createdAt": "UTC ISO timestamp", "data": {} }`. Data object keys are recursively sorted; payloads are bounded to 64 KiB, eight nested levels and 100 items per object/array. Headers include `X-Slotra-Event-Id`, `X-Slotra-Delivery-Id`, `X-Slotra-Event` and the timestamped signature above, generated with the endpoint's current secret version. The same event ID/body is reused on retry; consumers must deduplicate event IDs because a crash after receipt but before acknowledgement can cause another attempt.

`runWebhookWorkerOnce` processes a bounded batch sequentially with a required injected transport and a maximum five-second timeout per attempt. It retries unsuccessful attempts after 1, 5, 30, 120 and 360 minutes, then stops after six claims, including abandoned claims. Stored failures contain only HTTP status or safe internal codes; raw responses, exception details, signing secrets and credential-bearing URLs are not logged. `recordWebhookAttempt` now requires a claim fence; the previous unfenced test caller was updated. PGlite tests cover claim races, abandoned-lease recovery, replay/stale receipts, retries, fake-transport timeout, secret rotation, tenant isolation and endpoint/plan rejection. Independent-connection PostgreSQL acceptance remains open.

Before real delivery can be enabled, approve the payload and destination policy and implement/review an HTTPS transport with connection-time public-IP resolution/pinning, DNS-rebinding and SSRF protection, TLS hostname verification, redirect rejection and bounded response handling. A protected scheduler/worker deployment, operational observability and independent-connection/real-receiver acceptance are still required. No provider credentials or production network capability were added by the local worker work.

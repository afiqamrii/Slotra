# Pro multi-branch model

Pro inherits Business and allows up to five active branches under one organization. A branch is a location, not a tenant: all rows remain organization-owned. The owner/admin branch form creates a branch with its own address, IANA timezone, weekly hours, and sport base prices; courts/spaces and maintenance blocks belong to that branch. Reopening a paused branch rechecks the active-branch cap. Non-disabled resources are capped centrally at 1,000 for Pro.

The HttpOnly `slotra_branch` cookie chooses All Branches or a specific branch. It is a preference, never an authorization token. `branchContext` looks up active organization branches and intersects them with `member_branches` for members whose scope is `SELECTED`; forged or stale IDs are ignored. Server actions verify ownership again. Custom roles and branch assignments live in `custom_roles`, `organization_members`, and `member_branches`. The default is `ALL`; the owner cannot be branch-limited through the UI. Services that have not been made branch-aware deny restricted members rather than returning organization-wide data.

Bookings, availability, calendar, available-now, resource mutations, booking-linked payment reads/receipts/refunds, and the branch switcher check the branch server-side. A staff member assigned to Kerteh cannot use Kemaman's ID to mutate or inspect those records. Organization-wide customer CRM, Business automation, and some older reports are intentionally unavailable to branch-limited staff until a branch-specific policy is designed; this is fail-closed, not a completed branch-specific implementation. Existing owner/admin organization-wide workflows remain available.

The All Branches dashboard and `reports/branches` use `proExecutiveReport`, which batch-loads tenant-scoped bookings, resources, hours, blocks, and corporate charges. Each branch's selected local dates are converted to UTC bounds using that branch's timezone; an event is attributed by scheduled start to exactly one branch. Totals add branch counts/value/paid/outstanding once, and utilization is `sum(booked usable minutes) / sum(usable minutes)`, not an average of percentages. Current opening hours and maintenance status estimate past utilization and are not historical snapshots. Resource Performance means value and collected revenue, not profit. The booking query has a 50,000-row guard and report filters remain bounded.

The public guest booking page still selects the first active branch. A customer-facing branch selector, per-branch payment policy, full multi-branch customer CRM, staff schedule/automation targeting, and a larger-dataset query-plan review remain follow-ups. No separate deployment or database is created per branch.

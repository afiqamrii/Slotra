# Architecture

## Step 18 deployment and integration boundary

This section supersedes older phase notes about missing scheduling, storage and host-routing code. It describes implemented preparation, not a provisioned production environment. [INTEGRATION_READINESS.md](INTEGRATION_READINESS.md) records configuration and acceptance gaps.

`deployment-environment.ts` distinguishes local development, staging/Preview and production. `runtime-config.ts` validates core origin/auth/database configuration and approved target fingerprints. Supabase pooler/direct fingerprints canonicalize to one project/database. Staging additionally denies the known production target. Optional provider absence never becomes a startup requirement for manual booking. Administrative migration/seed scripts check target fingerprints before opening connections; migrations are never run by application startup or ordinary PR CI.

`integration-health.ts` provides OWNER/ADMIN, permission-checked, all-branch organization settings with normalized CONNECTED / NOT_CONFIGURED / MISCONFIGURED / DEGRADED states. Tenant merchant/domain rows stay scoped to that organization; platform email/storage/jobs/monitoring are labelled platform-owned. Configuration alone does not prove email/monitoring delivery: those states request verification instead of inventing a connection.

One protected `/api/internal/run-jobs` dispatcher uses PostgreSQL leases and the existing outboxes. Per-task cadence, bounded batches, fencing, backoff and interrupted-delivery reconciliation replace disconnected scheduler instructions. Vercel Cron is the intended single scheduler; its five-minute configuration is opt-in because the current deployment plan rejects that cadence. The baseline deployment does not install a schedule, and no second queue vendor is added. `0024_deep_demogoblin.sql` creates private platform job state and booking notification PROCESSING. It is pending external application. See [BACKGROUND_JOBS.md](BACKGROUND_JOBS.md).

Branding storage uses a dedicated private Supabase bucket. Authorized server uploads decode and re-encode still JPEG/PNG/WebP to WebP, strip metadata and use randomized `organizations/{organizationId}/branding/` paths. Logos accept 2 MB and covers 5 MB; input decode is capped at 24 million pixels, output within 512×512 or 1920×1080. SVG/animated files are rejected. Only the currently assigned published logo/cover is served through the narrow public branding route; generic organization files remain private/unimplemented. Storage credentials and actual bucket acceptance are still required.

Product origins are centralized in `product-urls.ts`; `proxy.ts` classifies configured marketing/app/book hosts and rewrites public booking into the same application. Unknown hosts fail closed. A customer hostname additionally needs verified+active tenant state, `CUSTOM_DOMAINS_ENABLED=true` and operator `CUSTOM_DOMAIN_READY_HOSTS` evidence of deployment registration/TLS. No automatic Vercel domain provisioning is claimed. The normal slug page remains the fallback.

Structured logs accept only bounded safe context. A minimal server Sentry adapter sends redacted event codes/context, with no SDK auto-capture of customer/request payloads. `/api/health` returns minimal core/database readiness. Monitoring configuration and alert delivery remain unverified. Legal draft routes and nullable venue cancellation/refund/rules fields (`0025_handy_blade.sql`, pending) expose policy text without inventing a venue policy or legal conclusion.

Resend has timeouts, no redirects, validated provider IDs and exact staging recipient restrictions. Production auth verification/reset remains a separately blocked credential-bearing delivery path; transactional booking email configuration does not resolve that blocker. Booking payments, SaaS billing and WhatsApp simulators are local-only; no selected live payment/subscription/WhatsApp adapter is implied. Outbound webhook signing/queueing remains distinct from actual HTTP delivery, which is not enabled.

See [DEPLOYMENT.md](DEPLOYMENT.md), [OPERATIONS.md](OPERATIONS.md), [BACKUP_RECOVERY.md](BACKUP_RECOVERY.md) and [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md). No infrastructure is marked configured from repository code alone.

## Production email boundary

All transactional email routes through `email-delivery.ts`, a server-only Resend adapter, and the shared escaped responsive templates in `email-templates.ts`. The adapter consumes `RESEND_API_KEY`, `EMAIL_FROM`, and optional `EMAIL_REPLY_TO`, uses persisted idempotency keys, and accepts delivery only when Resend returns a message ID. Missing configuration is a development preview or production failure, never a synthetic success. Safe logs contain no recipient, content, raw provider response, or secret.

Booking notification rows are inserted with the booking transaction, then delivered after commit; email failure cannot undo a booking. Subscription notice and scheduled-report outboxes keep their existing lifecycle and runners. Settings → Email delivery lets an active OWNER/ADMIN test only their own account address when configuration is valid. See [NOTIFICATIONS.md](NOTIFICATIONS.md), [DEPLOYMENT.md](DEPLOYMENT.md), and [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md).

## Step 16 subscription architecture

SaaS subscriptions are a separate bounded domain from venue booking payments. New organizations transactionally receive a dated Professional trial. The central catalog supplies prices and inherited limits/features; subscription-access resolves effective state and expiring admin overrides without trusting a browser plan. Authorization joins this resolution into the existing membership query; availability retains the existing bounded query count.

Owner Billing and Plans use server actions and a dedicated SubscriptionBillingProvider. Signed event verification, revision checks, organization/subscription locks, unique event claim and transactional audit/outbox changes are authoritative. Browser success cannot change the plan. Same-cycle upgrades preserve quota dates; scheduled downgrade/cycle switch/cancellation take effect at renewal. Expired/trial/suspended access retains data and basic read/export/billing. A bounded protected runner reconciles lifecycle/notices; it needs deployment scheduling.

Only an explicitly development-only provider is registered; production checkout is unavailable. Existing plans are preserved as LEGACY, not represented as paid subscriptions. Platform /admin is outside the tenant shell and requires users.platform_role=SUPER_ADMIN on every service. See SAAS_BILLING.md and SUPER_ADMIN.md. Older rollout notes below describe historical phases; their plan-code/UTC-month/one-time-upgrade statements are superseded by this section.


**Status:** Subscription/Super Admin foundation is implemented with migrations through 0023 applied. Automated checks, Webpack build and core isolated billing/admin browser/mobile flows pass. Independent-connection PostgreSQL acceptance, live production providers and final hardening remain pending.

## Step 15 Pro boundary

`plan-entitlements.ts` centrally inherits Business into Pro and sets 10,000 first confirmations, five active branches, 1,000 non-disabled resources, one owner, and 15 staff. A branch remains a child of the organization, never a separate tenant. `branch-context.ts` stores All Branches or a validated specific branch in an HttpOnly cookie; every use rechecks organization ownership and selected-staff branch assignments. `venue-service.ts` serializes branch creation/reactivation against the plan cap. Staff with selected-branch scope fail closed in older organization-wide services until those paths can explicitly supply an authorized branch.

`pro-reporting.ts` consolidates branch-local date windows, booking value, net collected, outstanding, utilisation and resource performance with tenant-batched queries; totals sum each branch once. Financial views require effective `report:view_financial`, not merely a base-role UI check. `custom_roles` store grouped allowlists, while `member_branches` limits operational access; OWNER remains nondelegable. The Pro audit stream records important new mutations and is paginated, but legacy Business mutations and invitations still need complete event coverage. See [MULTI_BRANCH.md](MULTI_BRANCH.md), [PERMISSIONS.md](PERMISSIONS.md), and [REPORTING.md](REPORTING.md).

The existing scheduled-report runner now distinguishes a Pro All Branches executive Overview from a specific-branch Professional-format report. Schedule timezone is the organization timezone for All Branches or the branch timezone for a selected location. Existing schedules are backfilled to a branch by 0021; sender and external scheduler limitations remain unchanged.

The versioned `/api/v1` Route Handler authenticates dedicated SHA-256-hashed, scoped organization API keys, never workspace cookies. Branch-bound keys narrow data access; queries are bounded and rate-limited. API writes reuse the booking/customer services. `pro-webhooks.ts` queues idempotent minimal events and signs payloads using server-derived HMAC secrets; endpoint setup and delivery history work, but outbound HTTP delivery is **not enabled**. The custom-domain model stores unique normalized hostnames and DNS TXT verification proofs, but verified domains stay inactive until application-host registration, certificate provisioning, and host routing are actually implemented. Public branding accepts restrained text/color/HTTPS images and no arbitrary CSS/JS. See [API.md](API.md), [WEBHOOKS.md](WEBHOOKS.md), and [CUSTOM_DOMAINS.md](CUSTOM_DOMAINS.md).

Corporate accounts do not replace customers. Approved customers may be booked by authorized staff against a monthly credit limit. The account row is locked while the existing booking engine creates the reservation and an applied corporate charge in one transaction; cancellation reverses it. This is usage accounting, not collection or an invoice. See [CORPORATE_ACCOUNTS.md](CORPORATE_ACCOUNTS.md).

## Step 14 Business boundary

Business inherits Professional through `plan-entitlements.ts` and adds centrally gated features; an enabled entitlement never substitutes for a service-level role/tenant check. `business-pricing.ts` owns branch-local weekday/time and sport/space rules. It rejects overlapping active rules of the same scope while a branch row lock serializes concurrent edits. A space-specific rule overrides a sport-wide rule; the existing base price remains the fallback. `booking-service.ts` and public availability use this same server price path, so a client cannot choose a rate. The current rule selects a single rate from the booking's **local start time** and applies it to the full duration; split-hour blended pricing is not implemented.

`business-recurring.ts` previews weekly occurrences using the common availability snapshot, then creates individual bookings through `createBooking`. A recurring series is metadata, not a multiweek reservation. Each successful occurrence receives its own booking and first-confirmation usage record. Conflicts are reported; an owner may create only available occurrences. Because creation and future edits process bookings one by one, a later race or failure can yield a partial series. This is visible in the result, not rolled back as an all-or-nothing batch. Editing one booking uses the ordinary reschedule operation; “this and future” reuses it for each future instance.

`business-benefits.ts` validates customer memberships, packages, and promotions inside the booking transaction. Membership discounts are applied from active, applicable plans; a scoped priority plan can extend the staff booking advance window, still capped by the venue Business policy. Package/membership minutes are row-locked and deducted for a whole eligible booking, with a usage record and cancellation reversal. Promotions are validated and usage-counted under a promotion row lock. A package or credit redemption cannot combine with a promo; a membership discount may combine with a promo, capped at the subtotal. Plan list prices do not perform a charge: membership assignment and package issuance are staff-administered until a separately verified purchase flow exists. Booking payment requirements calculate from the final server total; the normalized payment ledger remains the source of paid/outstanding amounts.

`business-segments.ts` derives deterministic customer cohorts from tenant-scoped booking history and stores manual tags in `customer_tags`; it does not infer consent or send marketing. `business-analytics.ts` joins those counts with Professional reporting and Business benefit ledgers. It explicitly leaves membership revenue and package sales untracked because manually granting a benefit is not a transaction. The Grow UI uses concise cards and template-first setup rather than an open-ended marketing rule builder.

`business-automations.ts` persists a small template set: 24-hour/2-hour **email** booking reminders and a 30-day inactive-customer tag. A secret-protected internal runner claims each workflow/target run key once, records its result, and performs delivery outside booking transactions. Development preview is not a sent email, and production skips email when its sender is unconfigured. The runner needs an external scheduler and a verified Resend sender to deliver production reminders. `whatsapp-provider.ts` defines the channel interface and a development-only success/failure/delay simulator; there is no live Meta adapter, customer consent store, or production WhatsApp delivery.

`business-waitlist.ts` accepts requests only for a genuinely full slot. A cancellation or reschedule can trigger a **post-commit, best-effort** email to the next eligible entry when email delivery is configured. It makes no reservation promise or exclusive claim window; the recipient must book through the same availability engine and exclusion constraint. `business-qr.ts` signs a booking reference with a server HMAC secret. Staff resolve it only after role/Business checks and check in through the existing legal status transition. QR codes contain no customer contact data. `business-rules.ts` stores optional organization policy for notice, advance horizon, maximum duration, buffer, and cancellation/reschedule cutoffs; it complements resource-level limits and never initiates a refund.

The current private `app` schema remains server-only. Applied migrations 0017–0019 add Business tenant tables, policies, and a membership-credit usage ledger with composite tenant foreign keys, RLS enabled, and no PUBLIC grants. Read-only post-apply checks found 20 migration entries and the Business tables on the connected main Supabase project; this does not substitute for browser or production-channel acceptance. Live WhatsApp delivery, external credentials, configured production email, and an external reminder scheduler remain deployment work; do not call an unconfigured channel delivered. Step 15 Pro work is described above. See `DATABASE.md`, `BOOKING_ENGINE.md`, `MEMBERSHIPS.md`, `AUTOMATIONS.md`, and `ROADMAP.md` for detailed state.

## Professional reporting boundary

`plan-entitlements.ts` maps Professional and higher tiers to `ADVANCED_ANALYTICS`, `ADVANCED_REPORTS`, and `SCHEDULED_REPORTS`. Report pages, CSV route, and schedule actions enforce an authenticated organization membership/role plus server-side feature checks. `professional-reporting.ts` owns validated period/filter resolution, batched tenant-scoped queries, timezone-aware grouping, and operating-window utilization; React only renders results. Starter retains its simpler operational reports. The Professional dashboard uses the same report service, not duplicated metric logic. A report query is capped to a 93-day period and 10,000 booking rows; there is no shared cross-tenant cache. See `REPORTING.md` for definitions.

Scheduled reports use tenant-owned `report_schedules` and per-recipient `report_deliveries`. The runner is disabled without a 32+ character secret, and delivery remains an explicit preview/failure until Resend sender configuration exists. This Professional reporting subsystem does not implement SaaS subscription billing.

The separate `plan-upgrade-service.ts` provides only a nonproduction Starter → Professional test. It creates an owner-scoped `plan_upgrade_attempts` row, uses the same ToyyibPay **sandbox** category via a distinct plan bill/callback, and requires signed callback plus independent provider transaction verification (or equivalent server-side verification after return) before changing the plan. The organization row is locked and repeat events are idempotent. A browser return alone is not trusted. The test does not create a recurring subscription, real invoice, renewal, or booking-payment ledger entry. A production Slotra SaaS merchant adapter remains future work; the Step 16 lifecycle supersedes this historical test.

## Starter operations completion

Starter's server-owned `organizations.plan_code` resolves through `plan-entitlements.ts` to feature flags and limits. `booking-usage.ts` persists one first-confirmation record in the same booking/payment transaction; an organization row lock serializes quota decisions across resources. Step 16 now uses anchored subscription windows, retaining UTC-month behavior only for legacy assignments. Resource creation/reactivation and member invitations enforce their caps in transactions; role/UI hiding is not the enforcement layer.

Dashboard, Customers, Reports, Plan & Usage, and CSV exports read tenant-scoped operational tables. Reports use branch-local booking start dates and server aggregates; the client chart only changes presentation (bar, trend, data) and metric choice (bookings, booking value, new customers). It does not calculate business totals client-side. CSV handlers require both organization permission and feature entitlement, limit rows, and neutralize spreadsheet formulas. No Professional analytics or billing workflow is implied.

Booking confirmation/reschedule/cancellation inserts a notification outbox record transactionally. Post-commit delivery uses a server-only email adapter and never rolls back booking success. The configured provider path is Resend; without it, the record remains a truthful dev preview or production failure. Production auth and team invitation delivery are still development-only and require separate approval and hardening before Starter is sellable to new venues. See `PLANS.md`.

## Principles

- Treat the system as a production SaaS with explicit tenant boundaries and server-side authorization.
- Keep domain rules separate from presentation components and transport concerns.
- Prefer small, clear modules and existing project patterns over premature abstractions.
- Keep the brand configurable and the domain model sport-neutral.
- Add dependencies when an implemented need justifies them.

## Current and intended stack

The repository has Next.js App Router, React, TypeScript, Tailwind CSS, ESLint, and `lucide-react` installed for the visual foundation. Supabase PostgreSQL, Drizzle ORM, the pg driver, and Zod environment validation now form the server-only database foundation. Better Auth and Vitest are integrated for authentication and tests. React Hook Form, TanStack Table, Recharts, date-fns, and Playwright remain future choices. Their exact roles and versions will be decided in the relevant implementation phase.

## Current presentation structure

The App Router keeps the landing, authentication, and live public booking route separate from the `(workspace)` route group. The workspace group shares a sidebar and top bar; a real organization context and placeholder route copy for later phases. `src/components` contains small reusable UI pieces, while `src/lib/brand.ts` centralizes temporary display branding. The workspace layout enforces session and active organization membership on each request; public pages remain accessible without a session.

## Intended domain boundaries

- **Tenancy and access:** platform, organizations, branches, users, roles, and authorization.
- **Venue setup:** sports, resources, operating hours, blocks, and maintenance.
- **Booking:** availability, lifecycle, conflict prevention, and recurring operations.
- **Commercial rules:** pricing, promotions, memberships, packages, and plan entitlements.
- **Payments:** payment state, provider integration, and reconciliation.
- **Customers and growth:** customer records, communication, and automation.
- **Reporting:** operational and financial views.

These are conceptual boundaries, not a prescribed folder structure, service split, or database schema. Booking, pricing, and payment rules belong outside React UI components.

## Database foundation

The first Drizzle migration creates a private `app` PostgreSQL schema. `src/db/schema.ts` defines the nine foundation tables; `src/db/client.ts` is a server-only connection entry point. Migration SQL is versioned under `drizzle/`. The Better Auth adapter and organization services now use the server-only connection; the connection is initialized on request. See `DATABASE.md` for constraints, migration and seed workflows, and still-pending access decisions.

The server reuses one bounded PostgreSQL pool per running application process, including across development route recompilation. Development processes use up to five connections. Production serverless instances use one connection with a shorter idle timeout and allowExitOnIdle, and must use Supabase's transaction pooler (port 6543) so horizontally scaled functions do not exhaust session-mode clients. Vercel functions are pinned to Tokyo (hnd1) in `vercel.json`, matching the Supabase ap-northeast-1 region to avoid cross-Pacific database round trips. Request-scoped React memoization deduplicates repeated session, membership, and plan reads shared by workspace layouts and pages; durable tenant data is still queried and authorized on each request. A successful migration-readiness probe is cached for the lifetime of a database client; missing-schema results and query errors are retried so a development migration can become visible without restarting.



## Phase 3 venue setup

Authenticated members with organization update permission (OWNER/ADMIN) can complete the ten-section onboarding wizard. The workspace dashboard shows a setup entry point until `onboarding_completed_at` is set. A single server transaction validates and creates the organization profile, selected sports, first branch, generic resources, branch operating hours, and branch/sport base rates, then marks completion. A browser-local draft retains progress before submission; it is not a server-side partial setup. Completing twice is rejected.

`src/lib/venue-service.ts` owns validation and tenant-scoped mutations. Server actions recheck membership; a branch ID or resource ID never establishes access. MANAGER may manage branch resources under the existing permission model when assigned. The `Courts & Spaces` and branch settings pages are live; Pro supports up to five active branches. Sport terms live in `src/lib/space-terminology.ts`, with a generic Space fallback.

The base-rate table is a minimal configuration foundation keyed by organization, branch, and sport, with an amount in minor currency units per 60 minutes. It does not calculate booking prices or availability and does not imply a rule engine. Branding stores a display name and accent color. Logo upload remains a clearly labeled placeholder because storage and access policy are not configured. The chosen slug now resolves the public booking page after onboarding and active-state checks.


## Phase 4 booking domain (code only)

`src/lib/booking-time.ts` converts local operating schedules to UTC windows using Temporal. `booking-availability.ts` batch-loads tenant-scoped resources, hours, blocks, and active bookings and exposes availability and slot generation independently of React. `booking-service.ts` owns authenticated staff creation, base-rate snapshots, resource blocks, rescheduling, cancellation, and legal lifecycle transitions. Phase 4 itself added no owner or public booking UI; Phase 5 adds the owner/staff workspace. The database exclusion constraint is the final active-overlap guard; services also serialize on the resource row. Migrations 0004–0005 are applied to the connected Supabase project; independent-connection concurrency acceptance remains pending.

## Phase 5 staff booking operations

The `(workspace)/bookings`, `calendar`, and `available-now` routes are server-rendered and tenant-scoped. `src/lib/booking-management.ts` provides bounded joined list/detail/search/calendar queries and live status derived from the booking availability snapshot. List history is paginated 50 at a time; calendar reads are capped at 500 bookings and blocks per branch/view, and customer counts are aggregated in SQL. The UI never calculates availability, conflicts, or prices. Server actions delegate creation, reschedule, status changes, and blocks to `booking-service.ts`; each service checks membership/permission and tenant ownership again.

The quick manual/walk-in form obtains server-generated slots, supports existing-customer lookup and inline minimal customer creation, and saves the customer and confirmed booking in one transaction. Guest walk-ins are permitted without a customer record. Available Now uses current bookings, blocks, opening windows, and resource status; its Walk-In link preselects a space. The day calendar aligns bookings and blocks on a branch-local resource timeline; available links come from the slot engine. Week view is a compact seven-day overview. Click-based rescheduling uses the same domain operation with a server price preview and transaction-time revalidation. Temporary maintenance is a timed resource block, not a permanent resource-state change. No drag-and-drop is implemented; public guest booking is a separate Phase 6 entry point.

## Phase 6 public customer booking

`/book/[organizationSlug]` resolves the organization server-side in the same deployment. The host router maps `https://book.slotra.my/{slug}` to that internal route; development/shared origins retain `/book/{slug}`. The three first-party origins are derived from `NEXT_PUBLIC_PRODUCT_DOMAIN`, while verified Pro custom domains use their separate tenant lookup. Exact first-party hosts are allowlisted and unknown hosts fail closed. Invalid slugs, incomplete or inactive organizations, and venues without an active branch/sport return not-found. Public branch selection is still pending; the current public flow uses its established active-branch behavior. A verified custom-domain record does not activate routing. The route renders public venue metadata, restrained branding, server-generated opening/slot information, and a guest-only flow; it does not import workspace authorization.

`src/lib/public-booking.ts` is the narrow public adapter. It resolves the tenant from the slug, validates dates and resource ownership, batch-loads the existing availability snapshot, calls `evaluateAvailability` for every cell, and obtains the existing base quote. `src/app/actions/public-booking.ts` rate-limits availability and submissions and returns only safe messages. `createGuestBooking` calls the same booking transaction as staff creation: row lock, availability recheck, base-price calculation, active-overlap exclusion backstop, customer association, CONFIRMED status, and history. A client quote is only a stale-price check, never the saved total. The later Phase 7 foundation adds optional test-only payment holds; the default public path remains Pay at venue.

The confirmation route is `/book/[organizationSlug]/confirmation/[token]`. The URL token is 32 random bytes, stored only as SHA-256 in `bookings.public_access_token_hash`. Confirmation queries also scope by resolved organization and joins only customer-facing fields. Reference-only lookup is deferred; a booking reference alone never reveals customer details. Public data is read through the private `app` schema using server-only credentials, not browser Supabase access.


## Phase 7 booking payment foundation

The booking engine remains provider-agnostic. `payment-policy.ts` calculates server-side amount due from the engine quote; `payment-providers.ts` holds ManualProvider and a development-only TestProvider contract; `toyyibpay-sandbox.ts` and `toyyibpay-service.ts` add hosted sandbox bills, callback verification, and provider reconciliation; `payment-service.ts` owns settings, account connection, ledger recomputation, manual receipts, refunds, hold expiry, and idempotent verified events. Guests choose from tenant-enabled payment options at review. A manual choice snapshots NO_UPFRONT and confirms with the full balance outstanding; a sandbox choice follows the existing verified-payment hold path. The server rechecks the selected method against current organization settings and the connected test adapter. Guest booking uses the same short resource-locked transaction and stores immutable policy/due snapshots. Required online test checkout enters AWAITING_PAYMENT, protected by the overlap constraint until expiry; only the verified event confirms it. Pay-at-venue remains CONFIRMED. ToyyibPay sandbox bill creation runs after the booking transaction, outside resource locks. Its callback signature and independent transaction query gate the common idempotent payment transition; the browser return status cannot confirm a booking.

Settings → Payments is owner/admin controlled. Booking detail shows payment history, paid/outstanding, authorized manual receipt/refund actions; Payments lists tenant-scoped recent activity. Public confirmation distinguishes pay-at-venue, deposit, full payment, pending hold, failure/expiry, and development simulation. The webhook route is a Node.js Route Handler, not a browser action. The sweep endpoint is secret-protected for future scheduling. See `PAYMENTS.md` for the full state and deployment prerequisites. Migrations 0009–0011 were applied to the connected Supabase project; the sandbox adapter needs no further schema change and no payment demo data was seeded there. The shared test key is server-only, disabled in production, and never a live multi-venue merchant strategy. `src/lib/plan-entitlements.ts` centrally maps Starter/Professional/Business/Pro to online-payment, deposit, and online-refund features; `organization-entitlements.ts` resolves the trusted `organizations.plan_code` and enforces payment capabilities server-side. Existing venues default to Starter after migration 0012. Starter's effective checkout policy is manual/pay-at-venue even if older online settings remain stored; provider events for earlier holds still reconcile. Settings renders a manual-only Starter state and a Professional preview. Step 16 now implements a separate subscription lifecycle and development self-service changes; production SaaS checkout is not connected.

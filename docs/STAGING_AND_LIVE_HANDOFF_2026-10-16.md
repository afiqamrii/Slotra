## Where configuration belongs

Use **Vercel → the exact project → Settings → Environment Variables**, scoped to one intended environment. Store credentials/database URLs as **Secret** and public/non-sensitive settings as **Config**. Production and staging values must be independent. Changes apply to new deployments, so redeploy deliberately after approved configuration changes. [Vercel environment variables](https://vercel.com/docs/environment-variables)

For a dedicated staging project, use its Vercel **Production deployment target** with application `DEPLOYMENT_ENV=staging` when testing Vercel Cron. Cron invokes the project's production deployment; an ordinary Preview is not a substitute for scheduler acceptance. Keep Deployment Protection enabled where supported and verify authorized test/cron access without broadly exposing staging. [Vercel cron execution](https://vercel.com/docs/cron-jobs)

For any Preview of the existing live project, configure only isolated staging credentials and `DEPLOYMENT_ENV=staging`. Never share its production database or sender key. The application treats Preview as staging regardless of an attempted development flag.

## Ordered staging runbook

These are instructions for a later explicitly authorized operator run. Database migration, fixture writes, deployment, email tests and job execution below were not run by this handoff.

1. **Confirm the release target and freeze a revision.** Existing authenticated CLI inspection can read `afiq-amris-projects/slotra`; use that verified target or an explicitly approved separate staging target. Connector use separately needs its scope restriction resolved. Inspect actual Git linkage, production branch, current deployments, protection and schedules; the current project's root `.` and Node `24.x` are already verified. Package files are at this repository root; do not configure an extra nested `slotra-step15` directory unless the chosen Git repository actually contains one. Preserve existing work, review the final diff and record the exact release commit. Confirm whether a main merge would auto-deploy before merging.
2. **Establish independent targets.** Verify staging/production project references and regions in Supabase, not only connection-string text. Use a separate staging project with fictional data; choose a separate recovery target. Do not expose private `app` tables through browser Data API grants. Confirm the actual PostgreSQL/extension versions and private schema/grants. [Supabase environment separation](https://supabase.com/docs/guides/deployment/managing-environments)
3. **Install scoped configuration privately.** Set staging core/origins/secrets/denylist and keep jobs, simulators and optional providers off initially. Confirm the runtime is Node 24, matching CI. Validate every `NEXT_PUBLIC_*` value as public build-time configuration; staging-built origins must not be reused as a production artifact.
4. **Review and run clean verification.** On the final revision, run `npm ci`, `npm run lint`, `npm run typecheck`, `npm test`, and `npm run build -- --webpack` as the current CI does. Also verify the actual build command chosen in Vercel. Attach command results/revision/date; do not copy historical local pass counts into a new release receipt.
5. **Approve and migrate staging.** Inspect all SQL and the actual target journal, including tenant constraints, indexes, private grants and compatibility with the currently deployed app. Compute the nonsecret target fingerprint from the securely loaded connection; record only that fingerprint/project reference. A pooler/direct URL may intentionally map to the same Supabase project/database fingerprint. Do not automatically accept a mismatch.

   ```powershell
   # Prints a fingerprint only; does not connect or print the connection string.
   node --env-file=.env.staging.local --import tsx -e "const { databaseFingerprint } = require('./src/lib/runtime-config.ts'); const target = process.env.MIGRATION_DATABASE_URL || process.env.DATABASE_URL; if (!target) throw new Error('Missing target'); console.log(databaseFingerprint(target));"

   # After independent target approval and privately setting MIGRATION_TARGET_FINGERPRINT:
   node --env-file=.env.staging.local --import tsx scripts/migrate.ts
   ```

   The file must specify staging and the production denylist. The application uses `DATABASE_URL`; the migration script prefers `MIGRATION_DATABASE_URL` when supplied. Use the connection mode appropriate for each process. Do not use schema push or replay the same SQL through Supabase migrations as a second migration authority. Inspect the applied journal, all required columns and `bookings_active_resource_no_overlap` afterward.
6. **Verify sender readiness, then create controlled accounts.** In Resend add the selected domain, publish its exact provider-generated DKIM/SPF/return-path records in authoritative DNS, wait for verified status, and review DMARC with the owner. Configure only controlled staging recipients before signup/reset/invitation tests. Resend acceptance is not receipt: inspect the actual inbox and message headers. [Resend domain setup](https://resend.com/docs/add-a-domain)
7. **Deploy protected staging.** Deploy the reviewed revision to the confirmed staging target with staging configuration. No deployment is assumed from a build or a project-list entry. Check `/api/health` returns `200` with `status: ok` after core/schema validation; unavailable schema/configuration must return `503`, not a reassuring success. Verify auth/session access before adding fixtures.
8. **Create minimum synthetic fixtures.** Register/verify a controlled owner through the real flow, complete venue onboarding, add a sport/branch/space/hours/price, and invite the controlled teammate. If a guarded seed is deliberately chosen, verify the disposable target and exact seed fingerprint first. Never seed production. The base seed does not create a user account; the richer Professional seed has additional account/plan restrictions. New venues start an unpaid trial, not a paid subscription; agree any pilot extension before expiry. Platform administration requires separately verified/provisioned Super Admin access under [SUPER_ADMIN.md](SUPER_ADMIN.md), never a tenant role or fake payment event.
9. **Run smoke and critical browser acceptance.** Put `SMOKE_BASE_URL` and a real synthetic `SMOKE_VENUE_SLUG` in the private staging environment file, then run `node --env-file=.env.staging.local scripts/smoke-test.mjs` (equivalent to `npm run smoke` after explicitly loading that process environment). Its six checks are read-only; no required venue check may be skipped. Then complete the write-capable acceptance matrix below. Three production hosts need separate host/routing checks; one origin's smoke result does not verify all hosts.
10. **Enable and observe jobs deliberately.** After the correct migration, sender restrictions and compatible schedule are confirmed, set `CRON_SECRET`, `ENABLE_SCHEDULED_JOBS=true`, and staging-only `ALLOW_STAGING_JOBS=true`. Deploy approved configuration, invoke the protected endpoint using the Authorization header, and inspect persisted task/outbox evidence. Observe actual scheduled invocation. Disable legacy schedules so only one dispatcher runs. A cron configuration entry is not evidence of a successful run. [Job operations](BACKGROUND_JOBS.md)
11. **Complete monitoring and recovery acceptance.** Send a safe synthetic operational event to the configured sink and verify alert receipt. Confirm actual backup freshness/retention and restore fictional records into a separate recovery target. Recover and checksum a known storage object if uploads are enabled; database backups do not contain Storage object bytes. [Supabase backup scope](https://supabase.com/docs/guides/platform/backups)
12. **Record the staging decision.** Fill every applicable release row with environment, exact revision, date, operator, result and restricted evidence location. A failed or unrun mandatory gate stays open. Define allowed pilot features and deferred capabilities explicitly before requesting a production release.

## Production sequence after staging acceptance

1. Obtain the final approved production/pilot scope, target project/database, maintenance window, recovery point and exact release revision. Resolve any live-provider implementation gate before offering that feature.

3. Configure production secrets/origins separately, build the production revision with its production public values, and release only that accepted artifact through the approved Vercel process. 4. Add/verify the three first-party domains using the exact Vercel-issued DNS records, then verify HTTPS, marketing→app auth routing, public canonical URL and safe unknown-host behavior. These changes require domain/account control; no generic guessed IP/CNAME is provided.
5. Run read-only production health/auth-denial/host checks and the explicitly approved minimal operator acceptance; observe logs, jobs, email and alerts. Open the pilot only after the recorded release decision. Preserve real ledgers/history; app rollback does not roll back a schema or reverse a provider action.
